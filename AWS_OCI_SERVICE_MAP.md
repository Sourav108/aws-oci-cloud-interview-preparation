# Comprehensive AWS vs. OCI Capability Mapping Reference

> **Architectural Principle**: *Never assert that two cloud services are identical. Always evaluate capability equivalence alongside structural, architectural, and operational differences.*

This document provides senior and staff engineers with a bilingual translation layer between **Amazon Web Services (AWS)** and **Oracle Cloud Infrastructure (OCI)** across all major cloud domains.

---

## 🗺️ Master Capability Mapping Table

| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Virtual Machines** | Amazon EC2 | OCI Compute Instances | Elastic virtual machine provisioning on physical hypervisors | AWS uses fixed family sizes (t3, c6i, m6i, r6i) on Nitro. OCI provides **Flexible Shapes** (`VM.Standard.E5.Flex`) allowing custom independent OCPU and RAM allocation. | General backend microservices, batch processing, monolithic application hosting. | *In AWS, resizing requires changing instance type. In OCI, you can scale memory without touching OCPU count.* |
| **Bare Metal** | EC2 Bare Metal | OCI Bare Metal Instances | Dedicated physical servers without hypervisor virtualization | OCI offers direct non-virtualized physical servers with sub-millisecond cluster networking (RDMA / RoCEv2). AWS offers bare metal within EC2 families. | HPC, ultra-low-latency financial engines, high-concurrency Oracle RAC databases. | *OCI is built from the ground up on off-box virtualization (SmartNICs), meaning bare metal has identical network latency to VMs.* |
| **Containers (Serverless)** | AWS ECS / Fargate | OCI Container Instances | Serverless container execution without node management | ECS Fargate integrates tightly with AWS VPC and ALB/NLB. OCI Container Instances run containers directly with native VCN VNICs and instant startup, without orchestrator overhead. | Lightweight APIs, batch jobs, background tasks, containerized scripts. | *Fargate runs ECS tasks or EKS pods. OCI Container Instances are direct container runtimes, not Kubernetes-backed.* |
| **Kubernetes** | Amazon EKS | OCI Container Engine for Kubernetes (OKE) | Enterprise managed Kubernetes control plane | EKS charges $0.10/hr per cluster control plane. OKE offers a **Free Basic Cluster** control plane and an Enhanced Cluster for advanced add-ons. EKS uses VPC CNI; OKE uses VCN CNI or Flannel. | Cloud-native microservices, multi-tenant container orchestration, distributed pipelines. | *OKE provides turn-key native integration with OCI Identity and OCI Load Balancers with zero cluster management fees for basic clusters.* |
| **Serverless Functions** | AWS Lambda | OCI Functions | Event-driven, ephemeral compute execution | Lambda uses proprietary microVM architecture (Firecracker). OCI Functions is powered by open-source **Fn Project** and executes OCI-compliant container images. | Webhook processing, event stream filtering, S3/Object Storage upload triggers. | *OCI Functions packages every function as a Docker container image natively; Lambda supports container images or raw zip packages.* |
| **Object Storage** | Amazon S3 | OCI Object Storage | Scalable, highly durable key-value object store | S3 has multi-bucket namespaces per account; OCI Object Storage organizes buckets within a regional **Tenancy Namespace** and compartments. S3 charges for API calls and tiered storage. | Static assets, database backups, media hosting, data lake landing zone. | *Both provide strong read-after-write consistency. OCI Object Storage supports cross-region replication and auto-tiering directly within the bucket configuration.* |
| **Block Storage** | Amazon EBS | OCI Block Volume | Network-attached persistent block storage for VMs | AWS categorizes EBS by volume types (`gp3`, `io2`). OCI uses a single volume type with **Dynamic Performance Units (VPUs)** adjustable on-the-fly (0 to 120 VPUs/GB) without detachment or downtime. | Database data directories, root OS filesystems, stateful persistent volumes. | *In OCI, IOPS and throughput scale linearly with volume size and selected VPU rating, adjustable via API in seconds.* |
| **Shared File System**| Amazon EFS | OCI File Storage Service (FSS) | Fully managed POSIX-compliant NFS file system | EFS supports bursting and provisioned throughput modes. OCI FSS creates mount targets inside private subnets and supports snapshots and NFSv3. | Shared WordPress uploads, persistent shared logs, multi-pod container shared state. | *OCI FSS requires an explicit Mount Target (VNIC with private IP) within a subnet; EFS creates mount targets per AZ.* |
| **Virtual Networking**| Amazon VPC | OCI Virtual Cloud Network (VCN) | Software-defined isolated cloud network perimeter | AWS VPC is regional and spans all AZs; subnets are strictly **Zonal** (tied to 1 AZ). OCI VCN is regional; OCI subnets can be **Regional** (spanning all ADs) or **AD-specific**. | Core network isolation, multi-tier application segmentation. | *Regional subnets in OCI simplify routing and load balancing by default across all Availability Domains.* |
| **Network Security** | Security Groups & NACLs | Security Lists & Network Security Groups (NSGs) | Stateful and stateless firewall rules for packet filtering | AWS Security Groups attach to ENIs (stateful); NACLs attach to subnets (stateless). OCI **Security Lists** attach to subnets (can be stateful or stateless); **NSGs** attach to VNICs (stateful or stateless). | Microsegmentation, ingress/egress restriction, zero-trust network boundaries. | *OCI recommends NSGs over Security Lists because NSGs separate security policy from network topology.* |
| **Internet Egress** | NAT Gateway | NAT Gateway | Outbound internet access for private subnet resources | AWS NAT Gateway is single-AZ (requires 1 per AZ for high availability). OCI NAT Gateway is **Regional** and highly available across all Availability Domains by default. | Private instances pulling package updates or accessing external SaaS APIs. | *In AWS, multi-AZ resilience requires provisioning and routing to multiple NAT Gateways. | **Cloud Service Access**| VPC Endpoints (Gateway / Interface) | Service Gateway | Private access to public cloud services without traversing public internet | AWS uses Gateway Endpoints (S3, DynamoDB) and Interface Endpoints (PrivateLink powered by ENIs). OCI **Service Gateway** provides routing directly to all OCI services in the region via Oracle Services Network. | Pushing backups to Object Storage or pulling secrets without exposing VMs to the public internet. | *OCI Service Gateway does not require per-service interface endpoints; one Service Gateway can route to "All OCI Services in Region".* |
| **Cross-Network Peering**| VPC Peering / Transit Gateway | Local / Remote Peering Gateway (LPG/RPG) & Dynamic Routing Gateway (DRG) | Interconnecting multiple private cloud networks | AWS uses VPC Peering (non-transitive) or AWS Transit Gateway (hub-and-spoke). OCI uses **Dynamic Routing Gateway (DRG v2)** which supports full transit routing, cross-tenancy, cross-region, and on-prem IPsec/FastConnect. | Multi-account/multi-compartment networking, shared services hub, hybrid enterprise mesh. | *DRG v2 in OCI acts as both a virtual router and a transit hub, replacing the need for separate peering gateways.* |

## ⚖️ Key Structural Contrasts for System Design Interviews

### 1. Resource Organization: Multi-Account vs. Compartment Hierarchy
- **AWS**: Isolation boundary is the **AWS Account**. Enterprise architectures utilize AWS Organizations, Service Control Policies (SCPs), and multi-account architectures (e.g., Security, Logging, Shared-Services, Production accounts) interconnected via Transit Gateway.
- **OCI**: Isolation boundary within a single **Tenancy** is the **Compartment Hierarchy**. Compartments are logical boundaries that organize resources globally across regions. Policies cascade down the compartment tree. Multi-account complexity in AWS is often handled via nested Compartments in OCI.

### 2. High Availability: Availability Zones vs. Availability Domains & Fault Domains
- **AWS**: Regions contain multiple physically isolated **Availability Zones (AZs)**. Subnets are strictly zonal.
- **OCI**: Regions contain 1 or 3 **Availability Domains (ADs)**. Inside every AD, OCI provides **3 Fault Domains (FDs)**. A Fault Domain represents separate hardware racks, power distribution, and top-of-rack switches. Single-AD OCI regions provide anti-affinity protection across Fault Domains, whereas in AWS single-AZ architectures lack rack-level guarantees.

### 3. Network Firewalls: Security Groups vs. Security Lists vs. NSGs
- **AWS Security Groups**: Stateful virtual firewall attached directly to the Elastic Network Interface (ENI). Evaluated as a collective whitelist.
- **OCI Network Security Groups (NSGs)**: Directly equivalent to AWS Security Groups—attached to the VNIC, stateful or stateless.
- **OCI Security Lists**: Attached to the **Subnet** level, affecting all VNICs in that subnet. Can be stateful or stateless. Best practice: Use NSGs for application-specific rules and Security Lists only for broad subnet-wide baseline rules.
