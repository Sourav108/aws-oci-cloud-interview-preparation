# 03. Health Checks, Connection Draining & Sticky Sessions

## 1. Problem
In distributed production systems, zero-downtime deployments and graceful autoscaling depend entirely on how load balancers manage backend node lifecycles. When health check intervals are poorly calibrated, healthy servers under minor CPU load are aggressively evicted, causing traffic to cascade onto remaining nodes and collapsing the entire fleet. Furthermore, terminating instances during deployments without configuring **Connection Draining (Deregistration Delay)** cuts active TCP sockets mid-flight, dropping payments and throwing HTTP 502 errors to users. Finally, relying on **Sticky Sessions** without understanding traffic distribution turns horizontal autoscaling into an illusion by pinning thousands of users to a single hot node.

## 2. Cloud Concept
### Backend Pool Abstractions
- **AWS Target Group**: A logical grouping of compute targets (EC2 instance IDs, private IP addresses, or Lambda functions) associated with an ALB or NLB listener rule.
- **OCI Backend Set**: The equivalent logical grouping in OCI, comprising backend servers, a load balancing policy (Round Robin, Least Connections, IP Hash), and health check rules attached to an OCI Load Balancer or Network Load Balancer.

### Health Check Calibration: Liveness vs. Readiness
- **Liveness Health Check**: Verifies that the container or VM process is running and the web server is listening on its port.
- **Readiness Health Check**: Verifies that the instance is actually prepared to accept customer transactions (internal database connection pool is warm, local cache initialized, background thread pool healthy).
- **Hysteresis & Dampening**:
  - *Unhealthy Threshold*: Number of consecutive failed probes required to mark a target dead (typically 3 failures).
  - *Healthy Threshold*: Number of consecutive successful probes required to restore a target to active routing (typically 2 to 5 successes).
  - *Flapping Prevention*: Asymmetric thresholds prevent a struggling node from oscillating in and out of the pool every 10 seconds.

### Connection Draining (Deregistration Delay)
When an instance is deregistered (due to an Auto Scaling scale-in event, a rolling software deployment, or manual removal), the load balancer initiates **Connection Draining**:
1. It immediately stops forwarding **new** client connections to that target.
2. It keeps **existing** in-flight TCP connections open for a configured window (e.g., 30 to 300 seconds).
3. Once all in-flight requests complete (or the deregistration delay expires), the instance is terminated cleanly.

### Sticky Sessions (Session Affinity)
Directs requests originating from the same client to the exact same backend server for the duration of a session:
- *Duration-Based Cookies*: The load balancer injects a signed cookie (e.g., `AWSALB`) with a fixed expiration time.
- *Application-Based Cookies*: The load balancer inspects a custom cookie generated by the application code (e.g., `JSESSIONID`).

## 3. Mental Model
Think of load balancer backend management as a busy restaurant dining room:
- **Health Checks** are the maître d' checking on kitchen prep stations. If the grill chef is overwhelmed or burned out, the maître d' stops assigning new diners to the grill station until the chef catches up.
- **Connection Draining** is letting seated diners finish their dessert and pay their bill before closing the dining room for the night. You never kick dining customers onto the street mid-meal.
- **Sticky Sessions** is insisting that a customer must always be served by Waiter Bob. If 100 big-spending customers all insist on Waiter Bob simultaneously, Bob collapses from exhaustion while four other waiters stand idle.

```text
  │       - Socket gracefully closed via TCP FIN-ACK handshake

  │       - Target status transitions to 'Deregistered'
  ▼
  └──► 3. EC2 / OCI Compute Instance terminated cleanly with ZERO client dropped packets!
```

## 5. AWS Implementation
In AWS Elastic Load Balancing (ALB & NLB):
- **Deregistration Delay**:
  - Configurable on the Target Group from **0 to 3,600 seconds** (default: **300 seconds**) `[Doc: AWS Target Group Attributes, checked 2026-09-03]`.
  - *Best Practice for Microservices*: 300 seconds is too long for rapid CI/CD pipelines (slows deployments down by 5 minutes per batch). Reduce deregistration delay to **30–60 seconds** for stateless REST APIs.
- **Sticky Sessions on ALB**:
  - Supports both AWS-generated duration cookies (`AWSALB`) and custom application cookies.
  - Duration configurable from 1 second to 7 days.
- **Health Check Return Codes**: Configurable HTTP status code matching (e.g., `200-299` or `200,301`).

## 6. OCI Implementation
In Oracle Cloud Infrastructure:
- **OCI Backend Sets & Health Checker**:
  - The Health Checker runs within the load balancing engine, supporting HTTP, HTTPS, and TCP protocols.
  - Configurable `interval_in_millis` (default: 10,000ms), `timeout_in_millis` (default: 3,000ms), and `retries` (failure threshold) `[Doc: OCI Backend Set Health Checker, checked 2026-09-03]`.
  - Supports **regex response body inspection**: checks that the HTTP response body contains a specific string (e.g., `"status":"HEALTHY"`).
- **OCI Connection Draining**:
  - Configured directly on the Backend Set via the `drain` and `offline` attributes.
  - When a backend server is marked `drain = true`, the OCI Load Balancer stops routing new requests while allowing current transactions to complete.
- **OCI Session Persistence (Sticky Sessions)**:
  - Supports **Cookie-based Session Persistence**: Server-generated cookies or Load Balancer-generated cookies (`X-Oracle-BMC-LBS-Route`).
  - Supports fallback to IP-hash routing if cookies are disabled by client browsers.

## 7. Configuration
Comparing Target Group and Backend Set health check and draining configurations in Terraform:

### AWS Target Group with Calibrated Draining (Terraform)
```hcl
resource "aws_lb_target_group" "app_tg" {
  name                 = "app-microservice-tg"
  port                 = 8080
  protocol             = "HTTP"
  vpc_id               = var.vpc_id
  target_type          = "instance"
  deregistration_delay = 45 # Reduced from 300s to 45s for fast CI/CD!

  # Calibrated Health Check
  health_check {
    enabled             = true
    path                = "/healthz"
    port                = "8080"
    protocol            = "HTTP"
    interval            = 15 # Check every 15s
    timeout             = 5  # Timeout after 5s
    healthy_threshold   = 2  # 2 consecutive passes to heal
    unhealthy_threshold = 3  # 3 consecutive drops to evict
    matcher             = "200"
  }

  # Sticky Sessions (Duration-based)
  stickiness {
    type            = "lb_cookie"
    cookie_duration = 3600 # 1 hour
    enabled         = false # Disabled by default for stateless APIs!
  }
}
```

### OCI Backend Set with Connection Draining (Terraform)
```hcl
resource "oci_load_balancer_backend_set" "app_backend_set" {
  name             = "app-microservice-backend-set"
  load_balancer_id = var.load_balancer_id
  policy           = "ROUND_ROBIN"

  # Calibrated Health Checker
  health_checker {
    protocol           = "HTTP"
    url_path           = "/healthz"
    port               = 8080
    interval_in_millis = 15000 # 15s interval
    timeout_in_millis  = 5000  # 5s timeout
    retries            = 3     # 3 retries
    return_code        = 200
  }

  # Session Persistence (Load Balancer Cookie)
  lb_cookie_session_persistence_configuration {
    cookie_name        = "X-OCI-LB-Route"
    max_age_in_seconds = 3600
    is_secure          = true
    is_http_only       = true
  }
}
```

## 8. Data Flow
```text
The Sticky Session Request Traversal:
1. Client 1 (No Cookie) ──> Hits ALB / OCI LB: GET /api/v1/profile
2. Load Balancer selects Backend 1 (10.0.1.20) via Round Robin.
3. Load Balancer injects Set-Cookie header: AWSALB=EncryptedToken(Backend1)
4. Client 1 receives response, stores cookie in browser.
5. Client 1 sends Request 2 with Cookie: AWSALB=EncryptedToken(Backend1)
6. Load Balancer decrypts cookie token:
   * Identifies target preference: Backend 1.
   * If Backend 1 is healthy, routes directly to Backend 1 (Bypassing Round Robin!).
```

## 9. Security
- **Hardening Sticky Session Cookies**:
  - Sticky session cookies must always enforce `HttpOnly` and `Secure` flags to prevent client-side JavaScript access (mitigating Cross-Site Scripting / XSS session hijacking).
  - Both AWS ALB and OCI Load Balancers cryptographically sign session cookies to prevent clients from tampering with routing tokens to target specific backend nodes.

## 10. Reliability
- **The Dangers of Flapping Health Checks**:
  - If `unhealthy_threshold = 1` and `timeout = 2s`, a momentary 2.5-second garbage collection pause in a Java microservice will cause the load balancer to instantly evict the node.
  - The remaining nodes absorb the evicted node's traffic, experience memory pressure, pause for GC, and get evicted sequentially, causing a total rolling cluster collapse.
  - *Reliability Rule*: Always set `unhealthy_threshold >= 3` and set health check timeout to at least 2x the normal p99 response latency.

## 11. Scaling: Why Sticky Sessions Break Autoscaling
- **The Hot Node Phenomenon**:
  - Sticky sessions pin clients to specific instances.
  - If a large corporate customer or automated web scraper connects from a single IP/session, all their heavy requests hit the same backend server.
  - As traffic surges, the Auto Scaling Group launches 10 new instances. However, **existing sessions are pinned to the old instances**! The new instances sit completely idle at 1% CPU while the original instances crash from overload.
  - *Architectural Axiom*: **Design stateless applications**. Store user session state in a distributed cache (Amazon ElastiCache / OCI Cache with Redis) and disable load balancer stickiness.

## 12. Observability
- **Key Target Group Metrics in CloudWatch**:
  - `HealthyHostCount` vs. `UnHealthyHostCount`.
  - `TargetResponseTime`: Measures latency between load balancer and backend targets.
  - `TargetConnectionErrorCount`: Counts TCP resets or connection timeouts between LB and target.
- **OCI Monitoring Metrics**:
  - `HealthSummary`: Returns percentage of healthy vs. unhealthy backends per backend set.

## 13. Cost
- Health checks generate internal network traffic. While intra-VPC/VCN health checks incur zero data transfer fees, aggressive checks (e.g., checking every 5 seconds across 200 targets from 3 AZs) generate hundreds of internal HTTP requests per second, consuming application thread capacity and logging storage.

## 14. Failure Modes
- **The 300-Second Deployment Bottleneck**: A team leaves the AWS Target Group default `deregistration_delay` at 300 seconds. During a rolling deployment of a 10-batch service, each batch waits 5 minutes to drain, turning a simple deployment into a 50-minute ordeal.
- **The Zombie Instance Trap**: An application instance fails its readiness check but passes its OS liveness check. If connection draining is set to 3,600 seconds, the zombie instance continues running for an hour, holding open half-dead connections while rejecting new traffic.

## 15. Troubleshooting
When instances unexpectedly fail load balancer health checks:
1. **Check Local Listening Sockets**:
   - SSH/SSM into instance: run `ss -tulpn | grep 8080`. Is the process bound to `0.0.0.0:8080` or mistakenly to `127.0.0.1:8080`?
2. **Execute Local Health Check**:
   - Run `curl -Iv http://localhost:8080/healthz`. What HTTP code is returned? Does it return 200, or a 500/503 error due to an uninitialized database pool?
3. **Inspect Target Security Group**:
   - Does the backend security group / NSG permit inbound traffic on port 8080 from the **Load Balancer Security Group ID**?

## 16. Common Mistakes
- **Binding Health Checks to Downstream Dependencies**: Setting `/health` to execute `SELECT 1` on PostgreSQL. If PostgreSQL experiences momentary latency, the load balancer marks **all 50 application servers unhealthy simultaneously**, turning a minor database slow-down into a complete application catastrophe.
- **Enabling Sticky Sessions Without Expiration Limits**: Setting stickiness to 7 days. Long-lived active users remain glued to the same instances across multiple release cycles, preventing balanced distribution.

## 17. Trade-offs
| Feature | Enabled / High Value | Disabled / Low Value |
| :--- | :--- | :--- |
| **Connection Draining** | Zero dropped in-flight requests; clean rolling updates | Faster instance termination; risk of truncated HTTP 502s |
| **Sticky Sessions** | Keeps local in-memory session state valid | Destroys horizontal autoscaling balance; creates hot nodes |
| **Deep Health Checks** | Ensures node can talk to database before receiving traffic | High risk of cascading failure; adds load to dependencies |
| **Shallow Health Checks**| High cluster resilience; prevents cascading evictions | May route traffic to nodes with deadlocked internal pools |

## 18. Interview Questions
1. *During a rolling deployment of a microservice behind an Application Load Balancer, users intermittently report HTTP 502 Bad Gateway errors. What is the root cause, and how do you resolve it?*
2. *Why do Sticky Sessions (Session Affinity) undermine horizontal autoscaling, and how should a Staff Engineer redesign the system to eliminate stickiness?*
3. *Explain the architectural difference between a Liveness probe and a Readiness probe. Which probe should be wired to the cloud load balancer health check, and why?*

## 19. Interview Answer
**Exemplary Answer to Question 1**:
> "Intermittent HTTP 502 Bad Gateway errors during a rolling deployment are caused by a **race condition between instance termination and Load Balancer Connection Draining (Deregistration Delay)**:
>
> 1. **The Root Cause**:
>    - During a rolling deployment, the CI/CD pipeline or Auto Scaling Group issues a termination command to old version instances.
>    - If the backend application process (e.g., Spring Boot or Node.js) receives the `SIGTERM` signal and shuts down immediately, it abruptly closes active listening sockets.
>    - However, the load balancer's deregistration state takes a few seconds to propagate across all internal proxy instances. If the load balancer forwards an incoming request to an instance whose process has already stopped, the connection is refused, and the ALB returns an instant **HTTP 502 Bad Gateway** to the user.
>    - Similarly, if active in-flight requests take 5 seconds to finish, but the instance is forcefully terminated after 2 seconds (`SIGKILL`), in-flight connections are severed mid-stream.
>
> 2. **The 3-Step Architectural Solution**:
>    - **Step 1: Tune Deregistration Delay on Target Group**: Configure `deregistration_delay` to a reasonable buffer (e.g., 30–45 seconds). This instructs the ALB to immediately stop sending new traffic while preserving existing sockets.
>    - **Step 2: Implement Graceful Shutdown in Application Runtime**: Configure the application server to catch `SIGTERM`, stop accepting new requests, and allow active threads up to 25 seconds to complete in-flight transactions before exiting.
>    - **Step 3: Pre-Stop Sleep Hook in Kubernetes / Container Runtimes**: Add a 5–10 second `preStop` sleep hook in container lifecycle manifests:
>      ```yaml
>      lifecycle:
>        preStop:
>          exec:
>            command: ["/bin/sh", "-c", "sleep 10"]
>      ```
>      This ensures the load balancer has completely removed the pod IP from its target table before the container runtime sends `SIGTERM` to the process, delivering a 100% clean, zero-error rolling deployment."

## 20. Hands-on Exercise
**Objective**: Measure the effect of connection draining during an instance termination event.

### Verification Steps
1. Deploy an EC2/Compute instance behind an ALB/OCI LB with `deregistration_delay = 30`.
2. Run an HTTP endpoint that sleeps for 10 seconds before returning HTTP 200: `/long-task`.
3. From a client terminal, initiate the request: `curl http://<lb-ip>/long-task`.
4. While the request is in-flight, trigger target deregistration via CLI:
   ```bash
   aws elbv2 deregister-targets --target-group-arn <tg-arn> --targets Id=<instance-id>
   ```
5. Observe the client terminal: the curl command returns `HTTP 200 OK` successfully after 10 seconds, proving the load balancer kept the in-flight socket open until the transaction completed.
